## 模型选择

| 模板 | 建议模型 | 新权重 | 实际判断依据 |
| --- | --- | --- | --- |
| 人员在岗监测 | 现有 `models/border/yolo11n.pt` | 不需要 | 岗位区域内人员数量与持续缺员时间 |
| 打瞌睡监测 | MediaPipe Tasks Face Landmarker，模型包 `face_landmarker.task` | 需要 | 眼部关键点计算的双眼开合程度与持续闭眼时间 |

YOLO11n 是已有通用目标检测器，官方资料列出约 260 万参数。它可以检出 person，但当前权重没有“闭眼”“打瞌睡”类别。无需为在岗监测重复训练模型。
官方资料：[YOLO11](https://docs.ultralytics.com/models/yolo11/)。

Face Landmarker 模型包集成人脸检测、面部关键点与可选表情系数；输出 478 个面部关键点，可选 52 个 blendshape 系数。它并不直接输出“睡着概率”，需要在模型输出上增加时序规则。
采用官方模型包和 Tasks API，不依赖旧版 `mp.solutions.face_mesh`。已固定并安装 `mediapipe==1.0.1`，与当前 Python 3.13 / Streamlit 环境共同运行验证通过。
先在独立目录验证模型加载和视频推理，再安装到正式虚拟环境；`pip check` 通过。OpenCV 与 opencv-contrib-python 固定同为 4.14.0.94，避免自动引入 5.x。
模型使用字节缓冲区加载，以避免 Windows 原生接口读取中文路径失败。下载脚本 `scripts/download_face_model.py` 校验 SHA-256：`64184e229b263107bc2b804c6625db1341ff2bb731874b0bcc2fe6544e0bc9ff`。
官方资料：[模型包与配置](https://ai.google.dev/edge/mediapipe/solutions/vision/face_landmarker)、[Python 视频接口](https://ai.google.dev/edge/mediapipe/solutions/vision/face_landmarker/python)。

不建议第一版采用未经本项目验证的第三方“睡觉 YOLO 权重”。YOLO11n-pose 可在后续辅助识别趴桌或头部姿态，但人体关键点不能判断眼睛是否闭合，低头看书也不能作为打瞌睡的充分依据。

## 人员在岗监测

这是“岗位区域是否有人值守”，不做人员身份识别，也不能区分值班员和路过的其他人。
用户上传视频、画出岗位区域、配置最低人数和允许缺员时长，随后开始分析。
区域应尽量覆盖实际工作位，避免把旁边的通道算进去；可复用当前矩形、多边形编辑器。

建议第一版参数：最低人数 1 人、连续缺员 5 秒报警、回岗稳定 1 秒解除、启动宽限 2 秒。这些是 Demo 初值，可按岗位要求调整，计时一律采用视频时间而非处理耗时。

规则名 `region_understaffed`，按区域维护状态：

1. 启动宽限期间显示“初始化”，不报警。
2. 每个成功推理帧统计区域内的 person，默认按检测框中心是否在区域内判断；后续可增加脚点模式用于地面区域。
3. 数量低于最低人数时，累计连续缺员时间；短暂漏检不足阈值不报警。
4. 达到阈值，生成一条 `post_unstaffed` 事件，区域变红，显示“岗位缺员：0/1 人，已持续 5.0 秒”。
5. 再次满足人数要求后，缺员连续计时清零；达到回岗稳定时长后解除已触发的报警，记录 `post_recovered`。
6. 持续缺员只记录一次事件。需要重复提醒时另设提醒周期，不能仅靠现有 cooldown 每过几秒重复导出事件。

视频一开始就无人，也应在宽限与缺员阈值后报警；不能只用现有 `leave_region`，因为它依赖先观察到同一目标从区域内移到区域外，目标消失时也不一定产生离开事件。
人数是区域级状态，不需要绑定某个 track_id，换人值守也能正常工作。
解码失败或推理异常必须显示“不可用”或终止该次分析，不能伪装成零人继续累积缺员时间。有效图像上持续漏检仍可能造成误报，需要用真实机位验证。

建议展示：绿色“在岗”、黄色“缺员计时”、红色“岗位缺员”、灰色“不可用”，并显示当前人数/要求人数和缺员进度。支持多岗位分别配置，不把多个岗位人数合并。

## 打瞌睡监测

当前以近距离、正面或轻微侧脸、眼睛清晰可见的视频为适用范围，支持最多 5 张人脸。远景监控、墨镜、严重侧脸和脸部遮挡不能可靠判断闭眼。
人员在岗样例分辨率仅 360×240，脸很小，不适合同时演示闭眼检测；打瞌睡样例使用独立近景素材。

处理链：视频帧 → Face Landmarker → 面部质量检查 → 双眼 EAR → 持续闭眼状态机 → 疑似打瞌睡提示。

EAR 是眼睛高度与宽度的几何比值。每只眼取 6 个关键点：

`EAR = (distance(p2,p6) + distance(p3,p5)) / (2 * distance(p1,p4))`

将归一化关键点转换成实际像素坐标后计算，避免非正方形图像使比例失真。关键点索引必须按 MediaPipe 的拓扑选取，不能直接照搬 dlib 的索引。
双眼分别计算；只有两眼均有效且都低于闭眼阈值才积累时间。不能用一个闭眼、一个睁眼的均值触发。

建议初始配置：

| 参数 | 初始值 | 说明 |
| --- | --- | --- |
| 闭眼阈值 | EAR < 0.20 | 仅用于起步调试，需按相机和人员标定 |
| 睁眼阈值 | EAR > 0.24 | 使用迟滞区间减小状态抖动 |
| 连续闭眼报警 | 2 秒 | 过滤短暂闭眼；非临床标准 |
| 睁眼恢复 | 0.5 秒 | 稳定睁眼后解除提示 |
| 最低有效人脸宽度 | 100 像素 | 工程质量门限初值，需用实际视频调整 |
| 处理帧率 | 目标 10–15 FPS | 按 CPU 实测调整；闭眼计时仍使用原视频时间 |

规则名 `eyes_closed_duration`。状态为“正常 / 闭眼计时 / 疑似打瞌睡 / 无法判断”。
从第一个有效闭眼采样点开始计时；到达 2 秒生成事件，在视频上标出眼部关键点、EAR 和“连续闭眼 2.0 秒”。稳定睁眼后解除，每次闭眼过程只触发一次。
检测不到脸、有效眼部关键点不足、严重侧脸或跳过过长时间时，中断本轮连续闭眼计时；缺失时间不能算进闭眼时间，也不能默认为睁眼。初版宁可漏掉被遮挡期间的闭眼，也不靠补帧虚构证据。
中间阈值区间保持短期平滑状态，但不足以无限延续闭眼证据；应设最大不确定间隔并在超时后重置。
同一岗位的人离开、另一人进入或目标关联不可靠时也必须重置，不能跨人累计。

可选的第二阶段：增加窗口内闭眼比例（PERCLOS 类指标）、反复点头和打哈欠作为辅助信息。
窗口应按有效观测时间计算并要求足够覆盖率；双眼几何阈值估计不能声称等同于标准化眼睑遮挡测量。
这些信号均不能单独证明已经睡着，界面保留“疑似打瞌睡”措辞。

## 接入后的演示与验收

人员在岗：上传 `on_duty_demo.mp4`，以区域 `(110,25),(250,25),(250,239),(110,239)` 作为初始岗位范围，再按预览调整。最低人数 1，缺员 5 秒，启动宽限 2 秒。
开头约 20 秒可见空场景，用于验证“从一开始无人也报警”；30–70 秒抽帧有人，用于验证在岗/回岗。末尾虽已离开，但缺员片段可能不够 5 秒，不能强行要求末尾一定产生第二次报警。

打瞌睡：上传 `drowsiness_demo.mp4`，闭眼阈值初设 0.20，连续 2 秒。抽帧显示约 2 秒处有一次较短闭眼，约 5–8 秒处可见持续闭眼，约 9 秒睁眼。
预期短闭眼不报警、长闭眼触发疑似提示、睁眼恢复；具体触发时刻需要接入模型后按关键点结果测定。
上传 `head_turn_control.mp4` 验证侧头本身不触发打瞌睡；严重侧脸应降为无法判断。

自动化验收重点：

- 岗位从开头无人、短暂漏检、持续缺员、稳定回岗、最低人数大于 1、多区域状态互不干扰、一次缺员只记录一次。
- 短眨眼、持续闭眼、单眼闭合、闭眼期间丢脸、侧脸质量不足、人员切换、恢复睁眼、抽帧率不同但秒数一致。
- 现有边防/火灾模板、DeepSeek 配置、视频叠加和事件导出不回归。
- 新依赖加载失败时给出可操作的错误，不能显示模板可用后在分析过程中静默改用其他模型。
